# Apache Dubbo Admin：Java 老版 vs Go 重构版 业务功能对齐对比

> 本文档由语义级代码阅读产出，用于核对 **Go 重构版（`develop` 分支）** 的业务能力是否与 **Java 老版（`java` 分支）** 对齐。

## 0. 对比基线与口径

| 项 | 老版 Java | 新版 Go |

### 0.1 AI 功能屏蔽说明

本次对比**已屏蔽全部 AI 相关功能**，理由与验证：

- Go 重构代码由 `#1302`（`[Break Change]: Transfer the source code from dubbo-kubernetes/refractor to here`）整体迁入，其后共 **56 个提交、PR 区间 `#1302` → `#1595`**，该区间内**不含任何 AI/Agent/LLM 相关提交**。
- `origin/develop` 的顶层目录为 `.agents .github api app docs pkg release scripts ui-vue3` —— **不存在 `ai/` 模块**；`ai/` 目录仅存在于 `ai` 分支（`git ls-tree -d --name-only ai` 可见 `ai`）。
- 对 `pkg/`、`app/`、`api/`、`ui-vue3/src/` 全量检索 `AIAssistant|llm|LLM|openai|OpenAI|anthropic|chatCompletion|prompt` → **0 命中**。
- 因此**对比天然限定在纯业务能力上**，无需额外剔除动作。`.agents/skills/` 为 Claude Code 侧的开发辅助 Skill，非产品代码，不计入业务能力。

## 9. 结论

1. **核心治理主链路已对齐**：条件路由、标签路由、参数覆盖三类规则的 CRUD + 表单/YAML 双模编辑，Go 侧在粒度、版本管理、灰度、服务级配置上**明显超越** Java。
2. **Java 的「长尾治理开关」在 Go 重构中整体丢失**：访问控制、负载均衡、Mesh 路由、Mock 打桩、API 文档、Dubbo YAML 配置管理 —— 这 6 项在 Go 树中**无任何后端代码**（`grep` 0 命中），其中 4 项前端也仅剩 29 行占位页。**这是本次对比最重要的结论**。
3. **基础设施广度收窄明显**：注册中心从 Java 的 10+ 种协议收敛到 3 种；Helm / docker-compose / 二进制发行版 / 发行流水线全部缺失（且 `release.yaml` 调用的 `make build-dubboctl` 目标在 Makefile 中不存在，属可验证的流水线断裂）。
4. **可观测性是 Go 侧最大增量**：Grafana 面板体系、Prometheus/PromQL、链路追踪、事件流、依赖拓扑、集群概览 —— 其中多数可追溯到 Go 树内陈旧的 Java swagger.json 所记录的历史 Java 端点（`/metrics/cluster`、`/metrics/flow`、`/metrics/metadata`、`/traffic/accesslog`、`/traffic/mock`），属「旧设计复活 + 现代化」。且 Java 的指标能力依赖 Dubbo 上游**已宣告废弃**的 `org.apache.dubbo.monitor.MetricsService`（Dubbo 3.2.5 标注 `@Deprecated`「will be deleted in the future」），Go 转 Prometheus 是**方向正确的演进**，不应按「能力倒退」计。
5. **存在 8 处可验证的实现缺陷**（非设计差异）：`/service/interfaces` nil handler panic、`/instance/search` 忽略 `appName`、`QosPort` 无写入点、`/instance/metrics-list` 无前端调用方、`/service/distribution` 忽略 `side`、`Tracing` 硬编码空串、Affinity/Script 路由缺失、release 流水线 target 缺失。
6. **AI 功能已完全屏蔽**：`origin/develop` 不含 `ai/` 模块，`#1302`→`#1595` 的 56 个提交中无任何 AI/Agent/LLM 提交，本次结论全部限于纯业务能力。
